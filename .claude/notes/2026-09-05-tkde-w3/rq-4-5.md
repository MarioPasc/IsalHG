## 2. Understanding and plan

**Restatement of the task in my own words:** Build three things in order: a shared
distance-matrix precomputation job whose `.npy` caches feed RQ2's census, RQ4 and
RQ5; the RQ5 clustering/geometry pipeline on the WD50K class-labelled corpus; and
the RQ4 anomaly-screening pipeline over injected corruptions. Each ships as a
runner + analyzer + config + SLURM launcher/worker pair, smoke-tested locally then
executed on Picasso with the matrices job as an `afterok` dependency.

**Approach chosen.** One module per deliverable, with `matrices.py` owning the
cache contract that the other two (and the peer's RQ2 census) read through. The
contract is enforced by a *strict* reader, `load_cached_matrix`, which raises
rather than falling back to computation: RQ4 and RQ5 run under walls sized for
reading a matrix, so a silent recomputation of a 7.95 M-pair arm is a TIMEOUT
several hours later with no diagnostic. Sizing decisions (task count, bundle
size, wall-clock) were taken from measured per-pair costs rather than from the
design document's estimates.

**Alternatives considered and rejected:**
- *Per-unit subprocesses in the worker loop* (the shape the `slurm/tkde/README.md`
  skeleton sketches) — rejected because each unit would re-load the collection,
  rebuild 3,988 hypergraphs and re-read up to 700 MB of cached matrices. Instead
  the runner owns the unit loop in one process and the start-cutoff moved inside
  it as `--deadline` / `--unit-budget`, which keeps the required semantics
  (including the first-unit exemption) while memoizing everything expensive.
- *A LOCALSCRATCH-staged matrices job* — rejected: the consumers run on other
  nodes and need the matrices at the shared path, and the payload is 26 large
  files, not the many-small-files pattern the staging rule targets.
- *Ordinary member-level bootstrap for the full-design ARI CI* — rejected after
  it produced an interval excluding its own point estimate (see §7).
- *Collection-major unit ordering for RQ4* — rejected: unit cost tracks
  sub-collection size (1,830 members vs 47), so an even split would give one
  multi-hour task and one four-minute one. Seed-major makes every bundle equal.
- *Splitting RQ5 across an array* — rejected: it is ~25 minutes of work in total,
  so an array would multiply scheduler load, which is the thing the two-hour
  floor exists to prevent.

**Plan as executed:**
1. Confirm worktree isolation, clone the conda env, read DESIGN §1/§5/§6 and CODE_PLAN.
2. Survey the exact APIs of the toolkit / corpora / stats / corruptions layers.
3. Read the Picasso infrastructure (`common.sh`, `PICASSO.md`, sync excludes, README).
4. Measure per-pair costs per arm to size everything.
5. Implement `matrices.py` + config + SLURM pair; local smoke.
6. Implement `rq5.py` + `analyze_rq5.py` + config + SLURM pair; local smoke.
7. Implement `rq4.py` + `analyze_rq4.py` + config + SLURM pair; local smoke.
8. Smoke test file; lint; format; full unit suite; `bash -n` on the workers.
9. Deploy, verify remote resolution, `--test-only`, submit, message the peer.
10. Harvest and run the analyzers on partial rows.

**Deviations from the plan:** three, all forced by measurement rather than by
preference. (a) The cost calibration was moved earlier, before writing the SLURM
layer, because the task count and wall-clock depend on it. (b) The start-cutoff
moved from bash into the runner (`--deadline`) once memoization made the
one-process-per-task shape clearly correct. (c) `--corpora-root` was renamed to
`--data-root` and given a resolver mid-flight, after the orchestrator relayed
that the frozen corpora live on FSCRATCH on Picasso but under the results root
locally.

## 7. Decisions, assumptions, open questions

**Decisions with a real trade-off.**

- *The strict cache reader raises instead of recomputing.* Costs: a consumer run
  whose dependency slipped dies instead of limping. Buys: the failure arrives in
  seconds with the missing `(collection, arm)` named, rather than as a TIMEOUT
  hours into a wall that was sized for reading a matrix, not building one. On a
  campaign this is the difference between a re-submit and a lost day.
- *Subsampling rather than bootstrapping for the full-design ARI interval.*
  Costs: a slight departure from the letter of DESIGN.md §6 ("member-level
  bootstrap CI"). Buys: an interval that is not biased upward. Resampling members
  *with* replacement duplicates them, a duplicate agrees with itself in both
  partitions, and every pair-counting index inflates — measured on the smoke
  configuration the ordinary bootstrap returned `[0.052, 0.098]` around a point
  ARI of `0.045`, an interval that does not contain its own point estimate. I draw
  `m = 0.632 n` distinct members instead (the expected distinct count of an
  `n`-out-of-`n` bootstrap), documented in the docstring and pinned by a test.
- *The PAM initialization for the full design is chosen by lowest PAM cost, not
  by best ARI.* Costs: a slightly worse reported ARI than cherry-picking would
  give. Buys: the criterion is label-free, so the reported number is not selected
  on the answer.
- *One process per SLURM task, with the start-cutoff moved inside the runner.*
  Costs: a departure from the `slurm/tkde/README.md` skeleton, which calls the
  runner once per unit from bash. Buys: the collection, its hypergraphs, its fact
  words and the cached matrices are memoized across units — measured 24 s -> 1.2 s
  per ndc_classes unit, and ~19 GB of repeat matrix I/O avoided on RQ5's balanced
  design. The required semantics are preserved exactly, first-unit exemption
  included, and tested.
- *RQ5 is one job, not an array; the matrices job is one job, not an array.*
  Both are below the two-hour floor. Both are single submitted jobs, which is
  ~1/1000 of the scheduler burden the floor was requested for, and slowing either
  by asking for fewer cores would delay the three research questions that wait on
  the matrices. Declared in both worker headers rather than left implicit.

**Assumptions I proceeded on.**

- *`wd50k100` has 7 usable classes, not the 8 that DESIGN.md §G4 states.* Measured
  from the frozen census: 925 / 572 / 52 / 34 / 29 / 26 / 22 at the `>= 20`
  threshold; the 8th class has 19. I used the measured threshold and made
  `analyze_rq5` report the count it actually used. Messaged to `main`, which
  replied that it is correcting §G4 to 7. If §G4 had meant a different threshold,
  the config's `min_class_size` is the one knob to change.
- *`iso_twin` is passed `budget = 1` and records it.* `corrupt` requires a
  positive budget and ignores it for twins (it swaps until nauty says
  non-isomorphic and records `n_swaps`). Recorded in the config comment, the
  module docstring and the rows.
- *Anomaly rows include anomaly-to-anomaly distances.* An anomaly's neighbours in
  the *modified* collection are what the screen sees; treating the other
  anomalies as their originals would score a collection that was never assembled.
- *`fact_rank` anomaly rows go through `fact_word` + `word_distance`, not
  `pairwise`.* Same distance, but one encoding per member instead of re-deriving
  the canonical labelling on both sides of every call.

**Open questions for the orchestrator.**

- *H5a's hubness clause fails at full scale.* Measured on the real 3,492-member
  `fact_rank` matrix: `nu = 0.1015` with 1,656 negative eigenvalues (the licence
  clause holds, so PAM over centroid methods and metric MDS over classical MDS
  are both licensed), but the `k = 10` hubness skewness is **5.408**, far above
  H5a's 1.5 ceiling. `analyze_rq5` reports the two clauses separately and states
  that a hubness failure does not withdraw the `nu` licence — but it does bear on
  RQ5's A -> A' gate and on how RQ4's kNN scores should be read, since hubness is
  the kNN precondition. Confirmed with `main`; final numbers come from the real run.
- *The LOF secondary score emits a sklearn "Duplicate values" warning on the
  naive floors.* Expected: `size_l1` takes few distinct values on 1,381 members,
  so many neighbours tie. The scores are still produced and the AUC is still
  well-defined; I did not suppress the warning because it is true.
