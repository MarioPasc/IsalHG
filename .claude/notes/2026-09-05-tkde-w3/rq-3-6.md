## 2. Understanding and plan

**Restatement of the task in my own words:** Build the two experiments that make the closed fact language visible — RQ3, which asks whether a decoded consensus word beats every method that can only return one of its inputs at recovering the reference record, and RQ6, which asks whether a sequence model over that language can only ever emit valid knowledge bases. Both must persist rows to the frozen schemas, be shardable and idempotent, run on Picasso under the group's job conventions, and be aggregated by analyzers that evaluate the pre-registered hypotheses on whatever rows exist. RQ3 additionally produces the certificate-validity rows RQ2 step 4 needs, because they come from RQ3's own matrices.

**Approach chosen:** One runner module per research question, each with a deterministic unit enumeration, a `--shard i/N` selector, per-unit incremental row writes and resume from the `unit` column; one analyzer per research question that globs the shards under `<experiment>/parts/` and writes the merged rows plus the six files at the experiment level. The RQ3 evaluation axis is implemented as two small pure functions over identity-addressed fact sets (`identity_facts_of_record`, `identity_facts_of_hypergraph`) so that the consensus output, a member and a majority merge are all scored by the same symmetric difference, and so the axis is unit-testable without any corpus. Wall-clock guards are process-level (a forked child that gets killed), because the C++ canonical-string call does not return to the interpreter on a signal.

**Alternatives considered and rejected:**
- *Per-shard table-name suffixes in one directory* (`rows_variants__shard000of008.csv`) — rejected because `write_config`/`write_summary`/`write_manifest` have fixed filenames and would clobber across shards. Shard directories under `parts/` keep all six files per shard and let the analyzer merge.
- *A merged `rows_certificate.csv` sitting beside the shard files* — rejected: a peer globbing `rows_certificate*.csv` would double-count. The shards live under `parts/` and only the merged file sits at the documented path.
- *Reimplementing reach-1 as three key comparisons* for RQ6's neighbourhood fraction — rejected as the recorded answer. The index is used only as an exact prefilter (it is `RemainderIndex.min_deletions`, the library's own machinery); every surviving candidate is confirmed by `language.reach` itself, so the number in the row is the library's.
- *Splitting RQ3 into 6–8 array tasks as the brief suggested* — rejected on measurement: the whole campaign is ~18 minutes locally, so those tasks would run ~6 minutes each, which is exactly the pattern SCBI asked us to stop submitting. Raised with `main`, accepted.
- *A time budget around every consensus call* — rejected for Corpus A (measured 0.05–0.5 s per collection, so the fork overhead would be a visible fraction of the reported `secs`) and kept for Corpus B, where a run can carry 40 members of up to 110 facts.

## 7. Decisions, assumptions, open questions

**Decisions with a real trade-off:**
- **Shard directories under `parts/`, merged files at the experiment level.** Costs one directory level and an analyzer pass before anything is readable at the documented path. Buys per-shard `config.json`/`manifest.json`/`summary.json` as the contract asks, with no clobber between shards, and a single unambiguous `rows_certificate.csv` for RQ2.
- **The process guard is applied to Corpus B only.** Costs uniformity. Buys `secs` on Corpus A that is the method's own time rather than the method plus a fork; Corpus A was measured at 0.05–0.5 s per collection, where a ~10 ms fork would be a visible fraction, while Corpus B carries up to 40 members of 110 facts and genuinely needs a wall.
- **The reach-1 index prefilters, `reach` decides.** Costs a class that duplicates part of `reach`'s reasoning. Buys a measurement that is affordable at all: the naive form is 1,000 samples × ~500 same-shape members × ~1 ms per pair per seed. The index is built from `RemainderIndex.min_deletions`, which the language layer made public for exactly this, and it is sound by construction, so it can only propose candidates, never reject a true one.
- **One array task, RQ6 bundled.** Costs parallelism and a single point of failure. Buys the longest available single task; mitigated by per-unit incremental writes and shard-level resume.
- **`io._repo_provenance()` and `io._cpu_model()` are called from both runners.** Costs a private cross-module call inside one package. Buys `git_sha` and `host_cpu` on every row that are the same values `manifest.json` reports; a second implementation would drift silently.

**Assumptions I proceeded on** (all four messaged to `main`; items 1, 2 and 4 confirmed, item 3 amended):
- The corpora base directory on Picasso is `$ISALHG_DATA_ROOT`, not the results root, so both workers pass `--data-root` explicitly. If this were wrong the runners would find no collection at all — loud, not silent.
- RQ2's analyzer reads `RQ2_wellposedness/certificate_validity/rows_certificate.csv` and not a recursive glob.
- Corpus B's unit is a maximal run of adjacent windows (`consecutive_runs`), one row set per run; a class with two separate runs of length ≥ 4 contributes both, distinguished by `run_index`.
- `regime_preserving` covers every consecutive pair inside the run, including the pair that ends at the truth quarter.
- Certificate rows come from Corpus A only, per DESIGN's "every variant collection".

**Open questions for the orchestrator:**
- `wd50k66 | del | N9` still drops 7 of 8 and 4 of 8 collections per seed even with the tightened pool (23 eligible sources, all with `m ∈ [10, 12]`): nine pairwise non-isomorphic single-fact deletions of a 10-fact knowledge base are simply rare. The drops are counted and reported; the cell will have thin data. In the meantime the runner proceeds with whatever collections it can build.
- `ndc_classes | del | N5` has exactly 8 eligible sources, so its status is `ok` only by one member and every seed draws the same eight sources. The recovery rate in that cell is therefore eight repeated sources under 27 different edit seeds, not 216 independent sources. Reported in `A9`.

### 15.2 Diagnosis — an unbounded memo cache, amplified by my runner

Memory **grows across units**; it is not a bounded peak. Reproduced locally on
`wd50k66` at the campaign's own settings (10,000 samples, `reach1_subset` 1,000),
RSS after each sample unit:

| unit | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| RSS (MB) | 3,725 | 6,683 | 9,442 | 12,112 | 14,693 | 17,357 | 19,980 | 22,673 |

+2.7 GB per unit, linear. The cluster's MaxRSS of 19,969 MiB sits between the
local unit-6 and unit-7 readings — a 0.06 % match against 19,980 MB — so the
20.4 GB is **RQ6's own trajectory**, and RQ3's peak is not implicated at all.

`Reach1Index._deletions` and `._keys` are *not* the leak: both saturate at 3,988
entries during the first unit and never move. An object census after
`gc.collect()` shows **zero** net Python-object growth per unit, and the only
surviving `SparseHypergraph` objects are the 3,988 collection members. The
growth is therefore allocation that Python still owns. `tracemalloc` names it:

```
S|wd50k66|fact_ngram|s60001: tracemalloc net diff=+733.1 MB
    +731.5 MB  src/isalhg/generation/ngram.py:276: count=17514 (+17514), average=42.8 KiB
```

`TokenNGram._distribution` memoises one dense `float64` vector over the whole
vocabulary per distinct sampling context, into `self._cache` — a plain `dict`,
unbounded, reset only inside `fit()`. Sampling explores ~17,000 fresh contexts
per unit, so each unit adds ~0.7 GB per 2,000 samples to a cache that is never
evicted.

The amplifier was **mine**: `CollectionContext.model(kind)` memoised the fitted
model in `self._models` for the life of the shard, so one model — and one
ever-growing cache — served all 27 seeds of a collection.

### 15.3 The fix

`CollectionContext.model()` now fits and returns a **fresh** `TokenNGram` per
call. The two call sites (`run_sample_unit`, `run_completion_unit`) call it once
per unit, so the memo cache dies with the unit. Refitting costs 0.15 s at the
worst measured collection (`wd50k66` fact alphabet, vocabulary 10,937) against a
~6 s unit, i.e. ~16 s across the whole 108-unit campaign.

Measured after the fix, same configuration, ten units:

```
S|wd50k66|fact_ngram|s60000  3722 MB   ...   s60009  3928 MB
```

Flat at 3.9 GB instead of climbing past 22.7 GB, and the reach-1 eligibility
counts are **identical** unit by unit before and after (885, 902, 896, 877, 911,
901, 894, 888), which is the evidence that the memo cache is a pure performance
cache and refitting changes no measurement. Pinned by three tests in
`TestModelIsNotSharedAcrossUnits`.

`src/isalhg/generation/ngram.py` was **not** touched — it is not this agent's to

### 15.7 For the orchestrator

1. **Library defect, not mine to fix.** `TokenNGram._distribution`
   (`src/isalhg/generation/ngram.py:276-290`) memoises a dense
   vocabulary-sized array per context in an unbounded `dict` with no eviction
   and no public way to clear it. Any long-lived `TokenNGram` that samples
   leaks ~0.7 GB per 2,000 samples. My runner works around it by not sharing a
   model across units; a proper fix (bounded LRU, or a public `reset_cache()`)
   belongs in `src/` and would help every other caller.

   touches `TokenNGram`.

   sound: the memo cache is a pure performance cache and the measured outputs
   are identical either way (§15.3).

   unseparated RQ3 peak; it can be cut to ~16G once a clean run reports MaxRSS.
